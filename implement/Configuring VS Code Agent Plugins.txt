Response: Here is a detailed guide on configuring a VS Code Agent Plugin, tailored with your specific project details.
Configuring VS Code Agent Plugins
Agent Plugins allow you to extend AI assistants in VS Code with custom skills, MCP servers, and hooks. The Agent Plugins 1.0 standard is designed for cross-tool compatibility, allowing the same plugin to work across different clients like GitHub Copilot and Claude Code.
1. The Plugin Manifest (plugin.json)
The core of your configuration is the plugin.json file. This manifest defines the plugin's metadata, schema, and capabilities. Based on your project, here is how you should structure the base manifest:
{
 "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
 "name": "codebridge-react-router-harness",
 "version": "1.0.0",
 "description": "Custom agent capabilities and routing harness tools.",
 "homepage": "labx.dev.br",
 "repository": "https://github.com/muraraallan/codebdrige-react-router-harness",
 "keywords": ["react-router", "harness", "agent-plugin"]
}

Required Fields
* $schema: Must be set to the canonical Agent Plugins schema identifier.
* name: Your plugin's unique package identifier.
2. Directory Structure and Namespaces
Your plugin's layout depends on the format you are targeting. For the standard Agent Plugins 1.0 format, the configuration lives at the root of your project:
codebdrige-react-router-harness/
 plugin.json              # Main manifest
 skills/                  # Custom skills
 mcp.json                 # MCP server configuration
 com.github.copilot/      # Client-specific namespace (VS Code/Copilot)
 .claude-plugin/          # (Optional) Claude-specific overrides

Cross-Tool Compatibility: Clients ignore reverse-domain namespaces they don't support. VS Code reads custom rules and hooks from com.github.copilot, meaning your plugin can safely include files for other environments without breaking VS Code.
3. Hook Configuration
Hooks allow your plugin to execute scripts at specific lifecycle events, such as PreToolUse or PostToolUse.
VS Code supports both a flat format and a Claude-compatible "matcher" format. Note: VS Code currently parses the matcher syntax but ignores the actual matcher values, meaning the hook will run on every matching event regardless of the filter.
Using Plugin Paths in Hooks
Because plugins are installed outside your active workspace, you cannot use relative paths to reference your scripts. You must use the ${CLAUDE_PLUGIN_ROOT} token, which VS Code expands to the plugin's absolute path at runtime.
Example Hook Configuration:
{
 "hooks": {
   "PreToolUse": [
     {
       "type": "command",
       "command": "${CLAUDE_PLUGIN_ROOT}/scripts/validate-tool.sh"
     }
   ],
   "PostToolUse": [
     {
       "matcher": "Write|Edit", 
       "hooks": [
         {
           "type": "command",
           "command": "${CLAUDE_PLUGIN_ROOT}/scripts/format.sh"
         }
       ]
     }
   ]
 }
}

Inside your bash script, you can also access this path via the $CLAUDE_PLUGIN_ROOT environment variable.
4. Developing Local Plugins
While building or testing your harness locally, you need to tell VS Code where to find the plugin without publishing it to a marketplace.
You can register your local directory by updating your VS Code settings.json:
"chat.pluginLocations": {
   "/path/to/local/codebdrige-react-router-harness": true,
   "/path/to/another-plugin": false
}

* true: Registers and enables the plugin.
* false: Registers the plugin but keeps it disabled.
5. Workspace Plugin Recommendations
If you want to ensure your entire team uses specific plugins when they open the project, you can configure workspace recommendations inside .github/copilot/settings.json (or .claude/settings.json).
When a team member sends their first chat message, VS Code will notify them to install these recommended tools.
{
 "extraKnownMarketplaces": {
   "labx-tools": {
     "source": {
       "source": "github",
       "repo": "muraraallan/plugin-marketplace"
     }
   }
 },
 "enabledPlugins": {
   "codebridge-react-router-harness@labx-tools": true
 }
}

Response: To achieve true write-once, run-anywhere compatibility across VS Code, Codex, Claude Code, and Google Antigravity, the secret is to separate your business logic (skills and tools) from your client manifests (how each AI reads the plugin).
Recent updates in the agent ecosystem—specifically the release of the Agent Plugins 1.0 standard and cross-CLI parsing improvements—make it possible to build a single repository without duplicating your tools or prompts.
Here is the blueprint for configuring the codebridge-react-router-harness repository so it is universally compatible.
1. The Unified Directory Structure
Keep your actual tools and instructions in universally supported formats (MCP and Skills), and use specific folders to serve the manifests each platform expects.
codebdrige-react-router-harness/
├── mcp.json                    # Shared MCP Server config (The Tools)
├── skills/                     # Shared Agent Skills (The Prompts/Knowledge)
│   └── route-scaffolding/
│       └── SKILL.md
├── scripts/                    # Shared executables for hooks
│   └── format.sh
├── plugin.json                 # Manifest for VS Code, Codex, Copilot (Agent Plugins 1.0)
├── .claude-plugin/             
│   └── plugin.json             # Manifest for Claude Code
└── com.github.copilot/         # (Optional) VS Code-specific UI extensions

2. Centralize Your Capabilities (Zero Duplication)
Instead of writing custom plugin code for each platform, rely on the two standards that all these platforms agree on: MCP (Model Context Protocol) and Agent Skills.
* mcp.json: Define your React Router scaffolding tools, validations, and AST parsers as an MCP server. Claude, VS Code, Codex, and Google Antigravity all natively consume MCP servers.
* skills/: Put your contextual markdown instructions here. The Agent Skills specification (SKILL.md) is universally recognized.
Because the tools and instructions live here, your client-specific manifests become lightweight wrappers that just point to these files.
3. The Agent Plugins 1.0 Manifest (VS Code, Codex, Cursor, Copilot)
At the root of your repository, create your plugin.json. This open standard is supported by OpenAI (Codex), GitHub (Copilot), and VS Code.
Because of the 1.0 standard, you don't even need to list your MCP server or skills in this file; compatible clients automatically discover mcp.json and the skills/ directory.
{
 "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
 "name": "codebridge-react-router-harness",
 "version": "1.0.0",
 "description": "React Router harness tools and agent capabilities.",
 "homepage": "labx.dev.br",
 "repository": "https://github.com/muraraallan/codebdrige-react-router-harness"
}

4. The Claude Code Layer
Anthropic relies on its own manifest located in the .claude-plugin/ directory. To prevent duplication, this manifest should simply point to the exact same shared resources.
Create .claude-plugin/plugin.json. Use the ${CLAUDE_PLUGIN_ROOT} token to reference your shared bash scripts so Claude can execute them seamlessly:
{
 "name": "codebridge-react-router-harness",
 "version": "1.0.0",
 "mcpServers": {
   "react-router-harness": {
     "command": "node",
     "args": ["${CLAUDE_PLUGIN_ROOT}/src/mcp-server.js"]
   }
 },
 "hooks": {
   "PostToolUse": [
     {
       "matcher": "Write|Edit",
       "hooks": [
         {
           "type": "command",
           "command": "${CLAUDE_PLUGIN_ROOT}/scripts/format.sh"
         }
       ]
     }
   ]
 }
}

Note: VS Code also parses Claude's matcher syntax, meaning this single hook definition can be safely cross-loaded if needed, without crashing VS Code.
5. The Google Antigravity Layer
Google Antigravity natively understands both MCP and local Skills. When you run the Antigravity CLI (agy) or its IDE Companion plugin, it will look for MCP servers to augment its capabilities.
Antigravity does not require a proprietary root manifest. By simply having mcp.json and the skills/ directory in your repository, Antigravity can ingest your harness tools directly into its subagents (like the Browser or Code subagent) without any extra configuration.
6. The Agent Profile Trick (Cross-CLI Quirks)
If you define custom agent profiles that restrict tool access, you'll encounter a syntax quirk: Claude uses a comma-separated scalar (tools: Read, Write), while legacy Copilot expects a JSON array (tools: ["view", "edit"]).
The Solution: Always use the Claude scalar format. The Copilot CLI and Agent Plugins 1.0 standard have been updated to natively parse the Claude-style scalar list. They will silently tolerate the Claude formatting, meaning you only have to write your agent profiles once.
By structuring the repo this way, your heavy lifting (MCP logic and Skill instructions) is written exactly once. The client manifests (plugin.json and .claude-plugin/plugin.json) act merely as lightweight pointers, ensuring you never have to duplicate a plugin definition.

User prompt: What is the exact schema and structure I need for the shared mcp.json file so it validates correctly across all these platforms?
Response: To guarantee cross-platform compatibility, your mcp.json file must satisfy both the legacy client formats (which rely on command signatures) and the strict Agent Plugins 1.0 specification (which forbids transport inference).
Here is the exact universal schema for a local stdio server.
{
 "mcpServers": {
   "react-router-harness": {
     "type": "stdio",
     "command": "node",
     "args": ["src/mcp-server.js"],
     "env": {
       "NODE_ENV": "production"
     }
   }
 }
}

Schema Requirements
* The Top-Level Wrapper: The entire configuration must be wrapped inside a root mcpServers object.
* Explicit Transport (type): You must include "type": "stdio". While older client configurations (like Claude Desktop) historically inferred the transport based on the presence of a command string, the new Agent Plugins 1.0 specification explicitly requires the type key to prevent clients from having to guess the network protocol.
* Execution (command & args):
   * command: The executable token (e.g., "node", "npx", "python"). Do not write the full shell string here.
   * args: An array of string arguments passed to the executable.
* Environment Context (env): An optional key-value object for injecting environment variables (like API keys or runtime modes) specifically for this server process.
By combining the explicit "type": "stdio" field with standard command arguments, this single mcp.json file remains perfectly valid for Claude Code, GitHub Copilot, Codex, and Google Antigravity simultaneously.
